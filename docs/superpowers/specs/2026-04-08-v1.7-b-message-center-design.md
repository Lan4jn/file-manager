# v1.7-B Message Center Design

## Scope

This design covers the `1.7` subset that should not disturb the main file-management workflow:

- Real-time in-app message center with a chat-style entry point at the bottom-right corner
- Feedback submission inside the message center
- User-to-user share forwarding from received share messages

This design intentionally excludes the remaining `1.7` file-management interaction changes.

## Goals

- Keep the existing left-sidebar reminder pattern for received shares:
  - `我的分享` continues to show `有X人分享给你`
- Add a more visible and more interactive message center without replacing the current share workflow
- Deliver new messages in real time via WebSocket
- Reuse the existing share model where possible
- Support forwarding a received user-share to other users with a newly generated share code

## Non-Goals

- Full IM semantics such as typing indicators, recall, message reactions, or cross-device read-state synchronization
- A separate feedback subsystem or ticket system
- Replacing all existing inbox and share management pages in this release

## Existing System Summary

- `ShareLink` is the persistent share carrier and is uniquely identified by `shareCode`
- User-directed shares currently create `UserShareMessage` rows, each pointing to a `shareCode`
- Opening a received share resolves the stored `shareCode` and uses the existing share-open flow
- The current inbox is a table view, not a conversation-oriented message center

This means forwarding cannot reuse the original row in place if the system must generate a new share code. The correct implementation is to create a new `ShareLink` and then create new user messages for the recipients.

## Recommended Architecture

Use `WebSocket + lightweight message model`.

### Why this approach

- It preserves current business flows instead of replacing them
- It gives immediate visibility through a bottom-right message panel
- It avoids overbuilding a full IM system
- It keeps the file-management core isolated from the new message-center behavior

## Data Model Changes

Extend `UserShareMessage` from a simple inbox row into a general message record.

### New/updated fields

- `messageType`
  - `SHARE`
  - `FEEDBACK`
- `body`
  - For feedback content
  - Optional for share messages
- `originSenderUsername`
  - The original sender of the share chain
- `forwardedByUsername`
  - The current forward operator
  - Only the latest forward hop is stored
- `relatedShareCode`
  - The share code currently associated with this message
- `conversationKey`
  - Used for lightweight grouping in the bottom-right panel

### Semantics

- Normal direct share from `A` to `B`
  - `senderUsername = A`
  - `originSenderUsername = A`
  - `forwardedByUsername = null`
- Forward by `B` to `C`
  - A new `ShareLink` is created
  - `senderUsername = A`
  - `originSenderUsername = A`
  - `forwardedByUsername = B`
  - `relatedShareCode = newShareCode`
- Forward again by `C` to `D`
  - A new `ShareLink` is created
  - `senderUsername = A`
  - `originSenderUsername = A`
  - `forwardedByUsername = C`
  - Earlier intermediate forwarders are not shown

This satisfies the user requirement:
- always show the initial sharer
- show only the current forwarder
- do not show deeper forward history

## Share Forwarding Rules

Forwarding is based on the received message, not on copying the original row.

### Forward behavior

1. The recipient selects a received share message
2. The user chooses one or more target users
3. The server resolves the share linked by the message
4. The server creates a new `USER`-targeted `ShareLink`
5. The new share uses:
   - a new `shareCode`
   - the system default expiration
   - no extra historical forward chain display beyond the current forwarder
6. New message rows are created for the new recipients

### Share expiry policy

Forwarded shares use the system default expiration period, not the remaining time of the upstream share.

## Feedback Rules

Feedback is not modeled as a separate subsystem in `1.7-B`.

### Feedback behavior

- Feedback is stored as `messageType = FEEDBACK`
- The sender creates feedback from the message-center panel
- The system routes feedback to administrator recipients
- Administrators see feedback in the same message center
- This keeps the architecture small and consistent

## UI Design

There are two message entry surfaces with different purposes.

### Left sidebar

Preserve the existing aggregated share reminder:

- `我的分享` keeps showing `有X人分享给你`
- This number is calculated only from unread `SHARE` messages
- The count is based on unique share-source users, matching the current behavior

Feedback messages must not affect this share-specific reminder.

### Bottom-right message center

Add a new floating message center entry at the bottom-right.

#### Closed state

- Floating round or rounded-square button
- Shows total unread message count
- Does not replace the left sidebar share reminder

#### Expanded state

- Two tabs:
  - `消息`
  - `我要反馈`
- `消息` tab:
  - reverse chronological list
  - no full contact/conversation roster in this release
- `我要反馈` tab:
  - category: `BUG` / `建议`
  - title
  - content
  - submit button

#### Share message card

- title: shared file/folder/batch-share name
- subtitle:
  - direct share: `初始分享人 A`
  - forwarded share: `初始分享人 A，由 B 转存`
- actions:
  - `打开`
  - `转存给用户`
  - `标记已读`
  - `删除`

#### Feedback message card

- sender
- category
- content preview
- created time

## Real-Time Delivery

Use WebSocket rather than polling or SSE.

### Endpoint

- `/ws/messages`

### Authentication

- Reuse existing token-based identity
- The WebSocket session is mapped to a single authenticated username

### Push model

The socket pushes events, not full business workflows.

#### Event types

- `message.created`
- `message.deleted`
- `message.read.local-refresh`
- `feedback.received`

#### Payload principles

- Include event type
- Include unread summary
- Include a message DTO when needed
- Keep payloads small and UI-focused

### Degradation

- If WebSocket disconnects, the page continues to function
- The message center can manually refresh over REST
- File-management features remain unaffected

## API Design

Keep REST for persistence and user actions. Use WebSocket only for delivery and refresh triggers.

### Message APIs

- Query messages with pagination and optional type filter
- Mark message as read
- Delete message
- Open linked share
- Forward a linked share to users

### Feedback API

- Submit feedback as a message

### Recipient API

- Keep the existing recipient query behavior for selecting target users

## Permission Model

Reuse authenticated-user access for personal message operations.

### Rules

- A user can only read, delete, and mark their own messages
- Forwarding is allowed only for messages owned by the current user
- Feedback submission requires only normal authenticated user access
- Admin recipients receive feedback messages automatically

If a dedicated feedback-management permission is needed later, it should be introduced in a future release rather than expanding this scope now.

## Backend Component Changes

### Extend existing services

- `UserShareMessageService`
  - message listing
  - feedback creation
  - forwarding workflow
  - message ownership checks
- `MessageController`
  - forward endpoint
  - feedback endpoint
- `ShareService` / `ShareLinkService`
  - helper to create forwarded user-targeted shares with origin metadata

### Add WebSocket support

- WebSocket configuration
- session registry by username
- message event publisher service

## Frontend Component Changes

### Keep existing pages

- `我的分享` and `收件箱` remain available
- The bottom-right message center becomes the primary visible real-time entry

### Add message-center state

- socket connection state
- unread summaries
- message list cache
- feedback form state
- forward-dialog state

### Interaction behavior

- incoming WebSocket event updates the floating panel state
- share reminders in the sidebar update in real time
- feedback submission appends local state after success
- forwarding success appends a local confirmation message or toast

## Error Handling

- Socket failure must not block file or share features
- Forward failure must not mutate the original message
- Invalid or expired upstream shares must return a clear message
- Missing recipient list must fail validation before forwarding
- Feedback submission must validate title and content length

## Migration Notes

- Existing `UserShareMessage` rows should remain valid after schema extension
- New nullable columns should be introduced with backward-compatible defaults
- Existing share-open behavior must keep working with legacy messages

## Testing Strategy

### Backend

Write tests first for:

- user-share message creation
- forwarded share creates a new `shareCode`
- forwarded message preserves `originSenderUsername`
- forwarded message stores only the current `forwardedByUsername`
- repeated forwarding does not display deeper intermediate history
- feedback message creation and routing to admins
- ownership enforcement for message actions

### Frontend

Test or verify:

- unread count calculation
- unique sender aggregation for `有X人分享给你`
- WebSocket event to UI refresh
- share-card rendering for direct share vs forwarded share
- feedback form validation and submission behavior

### Manual integration

- A shares to B and B receives a real-time message
- B forwards to C and C sees:
  - original sender A
  - forwarded by B
  - a new `shareCode`
- C forwards to D and D sees:
  - original sender A
  - forwarded by C
  - no mention of B
- Feedback submitted by a normal user appears for an admin in real time

## Risks

- WebSocket auth/session handling can become brittle if tied too tightly to existing HTTP assumptions
- Message-center UI can become noisy if all message types are surfaced identically
- Schema changes on `UserShareMessage` must be backward compatible with existing rows

## Recommended Implementation Order

1. Extend message schema and model
2. Add forwarding and feedback service/controller support
3. Add WebSocket delivery infrastructure
4. Build bottom-right message center UI
5. Connect sidebar aggregated reminders to the shared state
